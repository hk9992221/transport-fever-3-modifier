## 1. 根因

> **重要更正。** 本报告的第一版把根因写成「规则表用 `ipairs` 遍历」，
> 并把城镇需求写成「基线完全读不出」。**这两条都是错的**：
> 基线 `industryRules` 用的是 `for _,rule in pairs(rules)`，
> 而基线对官方文档的二元组需求结构实际上能读出来。
> 下面的缺陷是**用可复现探针逐条核实过**的，未经核实的说法已删除。

原实现 `src/功能接口v6.lua` 中可复现的缺陷如下。
它们都属于同一类：**关系被静默丢弃，而状态仍显示为「已读取」**。

### 1.1 资源目录里合法的货物编号 `0` 被丢弃

- Lua `cargoKey` 要求 `v>0`，因此编号 `0` 永远被丢弃。
- C# `IndustryCatalogPage.AddCargo` / `ReadTown` 也硬编码跳过 `"0"`。

`CargoTypeId` 是整数，`0` 是旅客货物编号，资源目录会列出它。
两端用硬编码常量丢弃 `0`，与规格 FIX-03 / AC-R06 冲突。

**探针**：规则输入引用编号 `0`、目录也列出 `0` 时，
基线得到空集合，当前实现得到 `0`。

### 1.2 以记录形式给出的货物引用被丢弃

`Rule.input` 的成员可能是记录（例如 `{cargoType=7}`）而不是裸数字。
基线只对裸数字调用 `cargoKey`，遇到记录直接返回 `nil`，关系静默丢失。

**探针**：规则输入为 `{ { cargoType = 7 } }` 时，基线得到空集合，当前实现得到 `7`。

### 1.3 小数编号被向下取整成另一个货物

`cargoKey` 先 `math.floor(v)` 再比较，编号 `1.5` 会被折成 `1`，
即「把小数向下取整成另一个货物」，与规格 FIX-03 冲突。

### 1.4 货物目录在产业读完之前就被封存

`ensureIndustryCargo` 在产业批次尚未读完时就固化了货物列表。
地图产业超过一页时，只在后续页规则里出现的货物编号会漏出目录。

**探针**：120 座产业、货物 `21`/`22` 只出现在第 120 座产业的规则里，
基线目录里两者都缺失，当前实现都有。

### 1.5 无法解释的条目被静默跳过，方向仍标为已验证

`collectOfficial` 遇到无法解释的条目直接 `return`，不计入未解析；
`industryRules` 对规则里无法解释的键也同样忽略。
结果：条目丢失，但 `inputStatus` 仍是 `verified`、`unparsedRuleCount` 仍是 `0`。
这正是规格 FIX-05 / FIX-06 明确禁止的行为。

### 1.6 「没有下游」与「尚未读完」被混为一谈

基线只要官方容器可读就标为 `verified`；`Analyze` 只看候选集合是否为空。
任何一个产业的规则读取失败，都会被展示成
「当前地图未找到消耗该产品的产业」，即用「没有」冒充「未读取」，与规格 §5.2 冲突。

### 1.7 多来源证据互相覆盖

基线 `addCargoRef` / `mergeRules` 用后写入的来源覆盖先写入的角色，
「一条规则中必需、另一条中可选」被合并成单一结论，与规格 FIX-07 冲突。

### 1.8 城镇需求：基线基本正确，第一版修复才是回归

官方定义（`api/engine.html` 原始 HTML）：

```
Engine.Component.Town.cargoNeeds: {{{CargoTypeId, number}}}
「list of cargo type ids for the needs of each of the three town districts
 residential, commercial and industrial」
```

该 wiki 的记号约定为：`{X}` 数组、`{K : V}` 映射、`{A, B}` 二元组。
因此 `{{{CargoTypeId, number}}}` 是
**三个需求区 → 每个需求区是 `{货物编号, 数量}` 二元组列表**。

基线用 `pairs(cargoNeeds)` 拿到三个需求区、再 `ipairs` 拿到二元组，
**对官方结构是正确的**。本轮第一版修复把它改成「以货物编号为键的映射」，
反而把数组位置当成了货物编号，属于**新引入的回归**，
已在审查中指出并修复。

当前实现同时接受二元组列表、按货物编号的映射、按需求区映射三种形状，
并且**永远不从数组位置推导货物编号**；无法解释的条目计入未解析。

### 1.9 「废料」的具体根因仍未确认

上述 1.1–1.4 都是**已被探针证实的「关系静默丢失」机制**，
其中 1.1（编号 `0`）与 1.2（记录形式引用）会让一条只以该形式出现的
消费关系整条消失，与「废料没有下游」的现象一致。

但**本轮没有取得真实存档样本**，因此不能断言废料的实际根因就是其中哪一条。
基线在「货物只存在于规则中、规则索引连续（`[1]`）」的场景下能正确识别，
所以不能把这个场景当作废料的根因。
真实根因需要按规格 §3.1 在问题存档中采集后确认。

### 1.10 本轮修复过程中引入、并已在复审中修正的两处问题

这两处不是基线缺陷，是上一版修复引入的，记录下来以免重复：

1. **改写宿主全局 `_`。** `readRecipe` 用 `_,officialInUnparsed=collectOfficial(...)`
   接收第二个返回值。Lua 中 `_` 不是保留的丢弃变量，这行会写入 `_G._`，
   破坏宿主同名绑定。已改为局部变量，并加边界探针 P14。
2. **嵌套分组里的未知成员被静默丢弃。** 官方分组与规则分组的成员循环只看
   `numericKeys`，`{ 7, unreadable = 'invalid' }` 这种「同一容器同时含合法与未知项」
   会把未知项丢掉却仍报 `verified`。现在会把非数字键计入未解析，
   方向变为 `partial`（探针 P12 / P13）。

## 3. 执行的验证

### 3.1 官方接口依据

已按 `api/engine.html`、`api/engine/util.html`、`api/type.html` 的**原始 HTML** 核对并引用：
`StockList.rules` 为映射、`Rule.input` 为 `{{integer}}`、`Rule.output` 为
`{CargoTypeId : integer}`、`Rule.booster` 为布尔、
`Town.cargoNeeds` 为 `{{{CargoTypeId, number}}}`（三个需求区，每个需求区是
`{货物编号, 数量}` 二元组列表）、`getInputsOutputsFromRules` 返回
`{{CargoTypeId},{CargoTypeId}}`、`getTownDistrictCenter` 的第二参数是单个
`LandUseType`。

`LandUseType` 的**数值未在文档中公布**，且官方记号中该类型是「单例记录」而不是数字枚举。
因此实现改为优先读取 `api.type.enum.LandUseType` 的 `RESIDENTIAL` /
`COMMERCIAL` / `INDUSTRIAL` 成员，读取不到时退回文档规定的数组位置顺序，
并且需求区中心的调用会依次尝试枚举成员与数字两种形式。

### 3.3 缺陷探针（`scripts/industry-lua-probes.lua`）

探针独立于 `industry-lua-check.lua`，可以同时对当前实现与基线运行，

| 探针 | 基线 | 当前 | 说明 |

| 零需求不虚构旅客需求 | 通过 | 通过 | 基线本来就正确 |
| 确认空方向不使配方变成未读取 | 失败* | 通过 | 基线无该状态字段 |
| 0 基稀疏官方列表不把偏移当编号 | 通过 | 通过 | 基线本来就正确 |
| 无法解释的官方条目不能是 verified | 失败* | 通过 | 基线无该状态字段 |
| 无法解释的规则组不能是 verified | 失败* | 通过 | 基线无该状态字段 |
| 显式刷新重试失败的货物目录 | 失败* | 通过 | 基线无该状态字段 |
| 只存在于规则中的货物仍是关系 | 通过 | 通过 | 基线本来就正确 |

| **后续页产业的货物仍在目录中** | **失败（缺失）** | 通过 | 真实行为差异 |

当前实现，不作为基线缺陷的证据。**加粗的三项是真实行为差异**，
也是 CI 中「基线必须失败」的依据。

### 3.5 持续集成

`.github/workflows/industry-regression.yml` 在 push 与 pull_request 上：
1. 用官方 Lua 5.4 运行 `scripts/industry-lua-check.lua`（必须通过）；
2. 运行 `scripts/industry-lua-probes.lua`（必须通过）；
3. 对冻结的缺陷基线再跑一次探针，**必须失败**——若探针在基线上也通过，
   说明它已经不再保护缺陷，工作流直接判定失败。

缺陷基线以冻结 fixture 形式保存在 `scripts/fixtures/industry-baseline-lua6.lua`
（修复前的适配层原文），因此合并后该守卫依然有效，不依赖 `origin/main` 是否可达。

工作流在 ubuntu-latest 上运行：Windows runner 需要 `step-security/msvc-dev-cmd`
才能编译 Lua，而该动作对私有仓库要求订阅；Lua 源码在 Linux 上不需要 MSVC。

```json
}
```

`verdict` 的取值与规格 §6.3 对齐：

| 取值 | 含义 |
| --- | --- |
| `selfConsistent` | 全图读取完整，且该货物的生产、消费、城镇集合非空并互相自洽。 |
| `notInCurrentMap` | 全图读取完整，且当前地图的规则与需求都没有引用该货物。 |
| `unverified` | 仍有产业、城镇或货物目录未读取，不能给出确定结论。 |

`mapComplete` 是 `index.Complete && CargoCatalogueComplete`；只要为 `false`，
**所有货物一律为 `unverified`**，不会因为恰好没有不确定计数就被判成自洽。

### 4.2 审计范围与边界

- 审计集合是**资源目录 ∪ 规则实际引用的货物 ∪ 规范化后的货物**，
  不是只遍历解析成功的那一部分。
- **本审计只是「实际集合清单」，不是独立核对。** 它只能回答
  「在已读取的数据里集合是否自洽」，**不能**发现解析器与游戏同时漏掉同一条关系。
  规格 §6.2 要求的 `expected - actual` / `actual - expected` 差异，
  必须另外提供**独立核验过的预期集合**才能计算；本轮没有该预期集合，
  因此审计结论**不构成**「产业链已完整核对」。
- 目录中没有被当前地图规则使用的货物会被标为 `notInCurrentMap`，
  不能据此宣称这些货物已通过真实生产链测试。

### 4.3 本轮审计执行结果

**未执行**：审计工具需要真实游戏进程，本轮未连接游戏，因此没有真实地图的审计结果文件。
离线合成数据的审计仅用于验证工具本身可运行，不构成地图结论。
