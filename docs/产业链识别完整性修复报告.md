## 1. 根因

原实现在 `src/功能接口v6.lua` 中存在以下确定性缺陷，它们共同导致「废料没有正确识别到下游产业」以及同类的其他漏识别。

### 1.1 规则表按数组读取，键为规则编号的规则被整体跳过（主因）

`Engine.Component.StockList.rules` 的官方类型是 `{[Rule]}`，即**以规则编号为键的映射表**；基线代码却用 `ipairs(rules)` 遍历。`ipairs` 在遇到第一个空洞时停止，映射表的键不是连续的数组下标，因此**绝大多数规则根本没有被读取**。

证据（官方定义，`api/engine.html`）：

```
record Engine.Component.StockList
  rules: {[Rule]}
  record Rule
    input: {{integer}}
    output: {[CargoTypeId] : integer}
    booster: boolean
```

同文件基线位置：`src/功能接口v6.lua` 的 `industryRules`（旧实现 `for _,rule in pairs(rules)` 与 `ipairs` 混用，
而 `readRecipe` 中以 `official` 为唯一方向来源）。

后果：只有官方汇总接口 `getInputsOutputsFromRules` 能确认的方向被保留；
只存在于规则中的消费关系（废料的典型情形：废料不是任何产业的官方汇总输入，
而是某条规则的输入组）整条丢失。这与「废料没有下游」的现象完全一致。

### 1.2 货物编号被两端无条件丢弃

- Lua `cargoKey`：`v>0` 才接受，因此编号 `0` 被丢弃。
- C# `IndustryCatalogPage.AddCargo` / `ReadTown`：`id == "0"` 时直接 `return` / `continue`。

`CargoTypeId` 是整数，`0` 是合法的旅客货物编号。资源目录是判定货物身份的依据，
两端却用硬编码常量丢弃 `0`，与规格 §4 FIX-03 冲突。

### 1.3 小数编号被向下取整成另一个货物

Lua `cargoKey` 先 `math.floor(v)` 再比较，编号 `1.5` 会被折成 `1`，
即「把小数向下取整成另一个货物」，与规格 §4 FIX-03 直接冲突。

### 1.4 城镇需求按「以需求区为键」读取，而官方结构是「需求区数组」

官方定义（`api/engine.html`）：

```
Engine.Component.Town.cargoNeeds: {{{[CargoTypeId] : number}}}
「list of cargo type ids for the needs of each of the three town districts
 residential, commercial and industrial」
```

基线代码按 `cargoNeeds[landUse] = { {id, amount} }` 读取。真实结构是
**三个需求区的数组，每项是 CargoTypeId 到数量的映射**。基线读法对真实结构
只能得到 `unread`，于是所有城镇供给关系全部消失，且被当作「该产品未识别到城镇供给用途」。

### 1.5 货物目录在产业读完之前就被封存

`ensureIndustryCargo` 在产业批次尚未读完时就固化了货物列表，
只在规则中出现、目录里没有的货物编号会漏出目录，跨层核对因此失真。

### 1.6 「没有下游」与「尚未读完」被混为一谈

`readRecipe` 只要官方容器可读就标为 `verified`；`Analyze` 只看候选集合是否为空。
任何一个产业的规则读取失败，都会被展示成「当前地图未找到消耗该产品的产业」，
即用「没有」冒充「未读取」，与规格 §5.2 冲突。

### 1.7 多来源证据互相覆盖

`mergeRules` 用后写入的来源覆盖先写入的角色与来源，
「一条规则中必需、另一条中可选」被合并成单一结论，与规格 §4 FIX-07 冲突。

## 3. 执行的验证

### 3.1 官方接口依据

已按 `api/engine.html`、`api/engine/util.html`、`api/type.html` 核对并引用：
`StockList.rules` 为映射、`Rule.input` 为 `{{integer}}`、`Rule.output` 为
`{[CargoTypeId] : integer}`、`Rule.booster` 为布尔、
`Town.cargoNeeds` 为三个需求区数组、`getInputsOutputsFromRules` 返回
`{{CargoTypeId},{CargoTypeId}}`、`getTownDistrictCenter` 的第二参数是单个
`LandUseType`。`LandUseType` 的**数值未在文档中公布**，因此实现改为优先读取
`api.type.LandUseType` 枚举成员，读取不到时退回文档规定的数组位置顺序。

## 4. 审计摘要

### 4.1 审计工具

`--audit <输出路径>` 会连接正在运行的游戏，调用**与产业推荐页面完全相同的
`industry_catalog` 接口**读取索引，再由 C# 侧生成机器可读 JSON：

```json
{
  "generatedAt": "2026-10-31T00:00:00.0000000Z",
  "source": "live-game",
  "revision": 12,
  "world": 3,
  "nameScope": "…",
  "complete": true,
  "industryCount": 320,
  "townCount": 28,
  "unreadIndustryCount": 0,
  "unreadTownCount": 0,
  "auditedCargoCount": 61,
  "rows": [
    {
      "cargoId": "9",
      "cargoName": "废料",
      "producers": ["1002", "1007"],
      "consumers": ["1001", "1015"],
      "townCandidates": [],
      "uncertainInputIndustries": 0,
      "uncertainOutputIndustries": 0,
      "uncertainTowns": 0,
      "verdict": "consistent"
    }
  ]
}
```

`verdict` 的取值与规格 §6.3 对齐：

| 取值 | 含义 |
| --- | --- |
| `consistent` | 该货物的生产、消费、城镇集合在完整读取下互相自洽。 |
| `notInCurrentMap` | 当前地图的规则与需求中没有引用该货物。 |
| `unverified` | 仍有产业或城镇的规则未读取，不能给出确定结论。 |

### 4.2 审计范围与边界

- 审计集合是**资源目录 ∪ 规则实际引用的货物 ∪ 规范化后的货物**，
  不是只遍历解析成功的那一部分。
- 预期集合与实际集合来自**同一次读取**，因此本报告只声明「集合自洽」，
  **不声明**「与游戏界面逐条核对一致」。后者需要真实地图实测。
- 目录中没有被当前地图规则使用的货物会被标为 `notInCurrentMap`，
  不能据此宣称这些货物已通过真实生产链测试。

### 4.3 本轮审计执行结果

**未执行**：审计工具需要真实游戏进程，本轮未连接游戏，因此没有真实地图的审计结果文件。
离线合成数据的审计仅用于验证工具本身可运行，不构成地图结论。
