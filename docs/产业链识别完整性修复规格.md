# 产业链识别完整性修复规格（废料与全货物回归）

- 状态：待实现、待游戏实测；本文是本轮修复与验收依据。
- 日期：2026-10-31。
- 仓库：`hk9992221/transport-fever-3-modifier`。
- 基线：`main@8b81429754ad0009315ffaed51000bd1f5c0a62f`，即已合并的 PR #3。
- 关联规格：[产业推荐功能规格（v1）](./产业推荐功能规格.md)。本文补充该规格 FR-04～FR-06 及 AC-05～AC-11 的准确性要求；未涉及的交互、定位、分页与地图隔离约定继续有效。

## 1. 问题与目标

用户在实际使用中发现：**“废料”没有正确识别到下游产业**。其他货物的产业链是否完整，目前没有足够证据。

本轮需要交付两个结果：

1. 找出真实存档中废料下游漏识别的原因，修复后能列出该地图上所有已确认消费对应废料货物的产业。
2. 对当前地图全部货物及产业执行上下游完整性核对，用集合差异找出其他漏识别或误识别，补充通用适配和回归测试。

“废料”目前只是用户看到的货物名称。其真实货物 ID、生产者、消费者类型、模组来源及生产机制均须从当前游戏取得，本文不预设具体下游建筑或固定配方。

本轮沿用现有“产业推荐”页面，修复数据读取、规范化、匹配和状态反馈。自动规划线路、计算最优整链方案、修改游戏配方不在范围内。

## 2. 已知实现与待查原因

以下是基线代码事实，不能直接当作废料问题的根因结论。

| 层次 | 基线实现 | 本轮核查重点 |
| --- | --- | --- |
| 游戏数据读取 | Lua `readRecipe` 调用 `getInputsOutputsFromRules`，再通过 `industryRules` 合并规则细节。 | 废料是否出现在官方返回、实际生效规则或其他经验证的消费入口中；是否漏读规则、关联库存或返回形式。 |
| 货物规范化 | Lua `cargoKey` 对数值取整并只保留大于 0 的值；C# `AddCargo`、`ReadTown` 排除字符串 `"0"`。 | 对照资源目录确认合法 ID 范围及表示方式；合法的 0 若存在，两端均不得丢弃。废料是否受此影响尚未确认。 |
| 货物目录 | `ensureIndustryCargo` 遍历 `cargoTypeRep.getAll()` 的表键。 | 实际资源 ID 在键还是值，稀疏目录和模组新增货物是否正确映射。 |
| 完整性状态 | `readRecipe` 在输入、输出均为 table 时即可将官方读取标成 `verified`。 | 返回容器可读不等于每项均已正确解释；不能静默跳过未知条目后仍宣称完整。 |
| 下游匹配 | C# `IndustryRelations.Analyze` 按 `consumer.InputIds.Contains(cargoId)` 查找消费者。 | 原始消费边是否在 Lua、JSON 分片、C# 反序列化、索引或页面筛选中消失。 |
| 测试 | 现有 Lua 检查和 C# 合成数据覆盖多项逻辑，但此前验收未连接真实游戏。 | 需要真实废料样本和贯通两端的数据测试，不能仅靠手工填好的 `Inputs/Outputs` 证明适配正确。 |

可能原因必须通过采样逐项排除。不得在尚未取得真实数据时，把“副产品”“ID 为 0”“库存兼容”或某一种返回结构认定为本次根因。

## 3. 修复前必须取得的证据

### 3.1 最小真实复现

在存在问题的存档中，记录下列信息。由实现者采集，不将补齐这些资料作为开始编写通用修复的前置用户问答。

| 项目 | 必须记录 |
| --- | --- |
| 环境 | 游戏版本、修改器提交、启用模组及版本、当前地图会话标识、索引 revision。 |
| 起点 | 用户正在分析的产业、其建设资源键、产业/建设/关联库存实体关系。 |
| 货物 | 页面名称“废料”对应的真实 cargo ID、可取得的稳定资源键和模组来源；同名货物分别记录。 |
| 预期下游 | 至少一个被漏掉的真实消费产业，以及游戏生产界面或实际生效规则中消费该货物的证据。随后扩展为该地图的全部预期消费者。 |
| 原始数据 | 起点和遗漏消费者的相关原始输入输出返回、规则结构、字段类型及可调用性；只采集分析所需字段。 |
| 中间结果 | Lua 规范化条目、实际发送的 JSON 分片、C# 解析后的货物集合和最终候选实体集合。 |
| 复现操作 | 选择起点、展开废料产品去向、清除会影响结果的筛选、刷新并取得全部分片；记录实际遗漏。 |

若起点只是库存中存在废料，而并非实际规则生产废料，须明确区分库存兼容与生产关系；不能为了让列表出现结果而把所有可存放废料的建筑加入产业链。

若游戏采用通用生产规则之外的回收、处置或特殊消费机制，必须取得该机制的真实入口和语义证据，再纳入统一消费关系。本文不假定这种机制一定存在。

### 3.2 定位丢失发生在哪一步

按以下顺序记录同一 cargo ID 和同一候选实体，形成可复查的证据链：

1. 游戏实际消费规则中存在该货物。
2. 游戏适配层读取到了对应规则或受支持的消费机制。
3. Lua 规范化结果保留了方向、ID 和消费角色。
4. 所有 JSON 分片传输后，条目仍完整。
5. C# 解析与索引保留该输入。
6. 分析结果包含消费者，页面能浏览、定位并继续分析。

根因说明必须指出首次丢失的步骤、触发数据形态及对应代码位置。真实样本经必要脱敏后保存为可重复运行的测试 fixture；保留 ID 一致性和结构，不保存凭据、完整存档或无关进程数据。

## 4. 功能与数据要求

| 编号 | 要求 |
| --- | --- |
| FIX-01 | 废料修复走通用货物和规则解析路径。以真实 cargo ID 匹配，不依据中文名、建筑名或固定消费者名单判断关系。 |
| FIX-02 | 货物身份以当前地图生效的资源目录和真实规则为依据。合法数值 ID、数字字符串及经证实的资源键统一为同一个规范化键；不同 ID 的同名货物保持分离。 |
| FIX-03 | ID 必须按合法格式严格校验，不能把小数向下取整成另一个货物。资源目录确认合法的 ID（包括适用时的 0）须贯通 Lua、JSON、C# 和城镇需求；空值、非法值与未知资源不能用 0 代替。 |
| FIX-04 | 枚举每座产业当前生效的全部规则及经验证的关联消费来源，覆盖多规则、多原料、多产物、副产品、替代输入和可选增产输入。当前库存、暂时停产、未开线路和当前产量为零不得取消有效关系。 |
| FIX-05 | 只按有证据的返回格式解析。数组、键值表、数量、分组和字段可读对象的语义须分别确认；禁止递归抓取所有数字当作 cargo ID。未知结构记录为未解析，不猜测。 |
| FIX-06 | 区分“输入读取状态”“输出读取状态”“角色读取状态”和“目录是否扫描完”。读取到容器不能直接推出内容已完整解析；空列表和读取失败必须分开。 |
| FIX-07 | 每条关系保留货物、方向、规则来源及角色依据。同一产业在同一货物的同一方向只出现一次；多来源或多角色可合并展示，但证据不能被最后一次写入覆盖。 |
| FIX-08 | 对当前地图全部产业和货物统一生成上下游关系。各类型消费产业均参与匹配，不默认按库存容量、当前产量、距离、已有线路或镜头范围隐藏。 |
| FIX-09 | 部分规则可读时继续展示已确认关系，并提示结果可能不完整。不能把其他产业的输入读取失败，仅归结为当前起点“没有下游”。 |
| FIX-10 | 新鲜度与原有地图隔离一致。刷新完成后使用同一 scope/revision 的全量分片重算；规则、产业等级或模组生效状态改变后，不继续沿用旧关系冒充新结果。 |
| FIX-11 | 产业消费者和城镇需求分别判断。废料不能因为某些成品可供给城镇，就自动获得城镇用途；其他货物原有的真实城镇需求、需求区距离和定位必须继续有效。 |
| FIX-12 | 提供按货物和产业追踪识别过程的诊断输出，并完成全货物审计与跨层回归。不能只修复一个名称对应的显示结果。 |

### 4.1 完整性与关系角色

“必需”“替代”“增产”“主产品”“副产品”是关系角色，不是决定候选是否存在的白名单。

- 真实输入中的替代原料和增产材料同样有下游消费关系，列表注明其角色。
- 副产品与主产品使用同一套去向匹配逻辑。若当前游戏规则证明废料是某产业的副产品，则应正常显示；若没有该证据，不强行标为副产品。
- 同一货物在多条规则中有不同角色时，保留各条来源；在一条适用规则中为必需、另一条中为可选，不能合并成“该产业所有生产都必需”。
- 当前等级不可用、未来解锁或仅存在于资源定义但未生效的规则，不混入“当前可消费”结果。无法核实适用条件时，说明未验证。
- 某产业既生产又消费同一种货物时，两个方向均保留。自循环保留在诊断中；候选列表沿用 v1 规则排除起点自身，多产业循环仍可逐级查看并返回。

### 4.2 多来源数据的合并

官方汇总、规则细节及特殊机制的证据须按来源记录。

能够确认的关系取并集并去重；一处来源未返回某货物，不足以推翻另一处已确认的生效消费规则。来源发生语义冲突、存在未解释的条目或适用条件不明时，标为部分读取并记录原因，不能悄悄选择一个来源后宣称完整。

仅角色或数量未知、但货物及方向已确认时，可以保留候选并标明角色或配比未读取；如果消费方向本身无法确认，则不得列为已确认消费者。

## 5. 关系定义和页面行为

### 5.1 统一的集合定义

在同一地图会话、同一已发布 revision 内：

- `P(c)`：当前规则确认生产货物 `c` 的产业实体集合。
- `C(c)`：当前规则确认消费货物 `c` 的产业实体集合，包含必需、替代和增产角色。
- `T(c)`：按单座城镇生效需求确认可接收 `c` 的城镇集合。

选择产业 `A` 后：

- 每个已确认输入 `c` 的供应产业是 `P(c)`，去掉 `A` 自身。
- 每个已确认输出 `c` 的下游产业是 `C(c)`，去掉 `A` 自身。
- 该输出的城镇去向是独立计算的 `T(c)`。

这里指直接上下游；不能把“某厂用该原料加工出的另一种产品还能供给的地方”误列为该原料的直接消费者。

距离只决定排序。坐标未知仍保留实体及可用的定位操作，分页必须能取完全部结果；计数按去重后的实体计算。

### 5.2 不再混淆“没有”与“未读取”

| 状态 | 页面要求 |
| --- | --- |
| 已确认有 N 个下游，相关消费数据完整 | 展示全部 N 个，按原规则排序、定位及继续分析。 |
| 已确认有 N 个下游，仍有产业或规则未解析 | 展示已确认 N 个，并提示“部分产业规则未读取，下游结果可能不完整”。 |
| 当前为 0 个，仍有产业或规则未解析 | 显示“尚未确认下游产业，部分规则未读取”，提供刷新；不能仅显示“当前地图未找到消耗该产品的产业”。 |
| 全图相关消费数据完整，确实为 0 个 | 显示“当前地图未找到消耗该产品的产业”；该结论只适用于当前地图及规则版本。 |
| 起点产物本身未读全 | 显示“产物部分读取/未读取”，不能把缺失的废料分组解释为无此产物。 |
| 坐标或角色未读取，但消费关系已确认 | 保留候选，分别显示距离未知、角色未读取，不能隐去建筑。 |

未解析规则如果连货物 ID 都无法确定，可能影响任意货物的候选完整性，不能只对已知几个货物报错。已成功读取的其他结果应继续可用。

主页面展示货物名、关系、距离、完整性和操作。原始资源键、实体 ID、规则片段及异常进入诊断，不堆到主要操作区域。

### 5.3 内部契约调整

在现有 `industry_catalog` 的行业、城镇和货物分片上扩展，避免为同一修复再建一套互不一致的目录。

至少能够表达以下含义，字段名称可按现有结构实现：

| 数据 | 必须表达的含义 |
| --- | --- |
| 扫描状态 | 产业枚举、各分片传输是否完成；与内容解析完整性分开。 |
| 读取状态 | 每座产业的输入、输出和角色是否完整，未解析规则数量及原因。 |
| 货物身份 | 当前会话内统一 cargo ID；可验证时附稳定资源键和来源，不以显示名称连接。 |
| 关系证据 | 目标实体、货物、方向、角色及对应规则/来源引用。 |
| 完整性 | 是否还有可能影响当前结果的未知消费规则；已确认候选数与待核验状态分别表达。 |

保留现有 `complete` 的完整性含义，不能为了消除警告改成“扫描走完即 true”。对旧字段做语义不兼容调整时升级 schema，并让 Lua/C# 作为同一版本交付；未知版本明确报错，不能静默生成空链。

诊断明细按需读取或单独导出，不把全图原始规则塞进周期状态。继续遵守每页最多 100 条、现有 480 KiB UTF-8 字节预算和单条超限明确报错的约定。

## 6. 全货物、全产业的完整性审计

### 6.1 审计范围

“全部”限定为**被验证的游戏版本、启用模组集合和当前地图实际产业**，不得凭一个存档或一组模拟数据宣称所有游戏/模组组合都已覆盖。

审计货物集合取以下来源的并集：资源目录、原始规则实际引用的货物、规范化后的货物。只遍历成功解析出的货物，会把被解析器漏掉的货物一起漏出审计。

每个实际产业均须有状态记录；读取失败的产业也计入覆盖范围和待核验数量。未放置在当前地图的资源配方，不直接算作地图上的供应者或消费者。

### 6.2 独立预期与集合比对

对每个货物分别列出预期 `P(c)`、`C(c)`、`T(c)` 和实际识别集合，记录：

- 遗漏实体：`expected - actual`。
- 误识别实体：`actual - expected`。
- 方向、角色或规则适用条件错误。
- 不能确定预期或实际结果的原因及覆盖范围。

预期集合来自独立核对过的原始样本、游戏界面/生效规则或人工标注 fixture，不能用被测解析器再运行一次生成答案。对同一规范化数据做双向一致性检查有价值，但双方同时漏掉废料时仍可能一致，因此不能作为唯一证据。

具有相同资源类型、规则形态及适用条件的产业可以复用人工核验过的解释，仍须逐实体检查是否存在例外。每一种实际出现的规则形态、消费机制、角色及生效条件至少有一份可追溯样本。

### 6.3 审计输出

实现 PR 至少附一份可机器读取的 JSON/CSV/TSV 审计结果，包含：版本及提交、会话/revision、货物 ID/名称、生产与消费实体集合、预期依据、遗漏、误识别、读取状态及未验证原因。

每个货物须落入“集合核对一致”“已核实当前地图无该方向关系”“未验证/数据未读全”之一。目录中没有被当前地图规则使用的货物可以明确标为未参与当前地图产业链；不能把它们全部算作已通过真实生产链测试。

交付报告列出已审计货物数、产业数、真实样本数、未解析规则数和未验证项，而不只给出一个“全部通过”。

## 7. 测试要求

### 7.1 四层验证

1. **Lua 适配层**：输入原始 API/规则 fixture，运行实际 `readRecipe`、目录构建和 `S.dispatch`，核对货物、方向、角色、完整性及全部分页结果。
2. **跨层数据链路**：将上述代码实际生成的 JSON 分片交给生产使用的 C# `IndustryCatalogPage.Read`、索引合并及 `IndustryRelations.Analyze`，比较完整候选集合。不能在两端分别手写互不关联的“正确对象”。
3. **页面层**：用同一份数据验证废料分组、完整性文案、全部结果、距离、定位、继续分析及历史；沿用现有离线布局检查。
4. **真实游戏**：回到原问题存档或具有同一生效规则的可复现地图，对照游戏中的真实消费者完成前后对比。

模拟、离线界面、真实游戏的结果分开记录。未连接游戏时可以交付离线修复，但“真实废料问题已验收通过”和“其他产业链已完整核对”必须保留为待验证。

### 7.2 核心验收用例

| 编号 | 场景 | 必须验证的结果 |
| --- | --- | --- |
| AC-R01 | 原存档中曾漏识别的废料链路 | 废料对应 ID 正确；原遗漏消费者出现；全部预期消费者集合一致，且没有仓库等误识别对象。 |
| AC-R02 | 废料由多种产业消费，角色或消费机制不同 | 各已验证机制的消费者都出现，按实际角色说明，不受建筑类型名单限制。 |
| AC-R03 | 多产物规则与副产品 | 所有真实产物均有分组和正确去向；其他产物不因修复废料而消失。 |
| AC-R04 | 多条规则、同货物多来源 | 同一方向按实体去重，来源可追溯；同货物在不同方向和不同起点下不被错误合并。 |
| AC-R05 | 必需、替代、增产输入及不同等级适用规则 | 有效消费者集合与角色正确，未生效规则不冒充当前消费，未知条件有提示。 |
| AC-R06 | 资源目录中存在合法 ID 0；如真实环境不出现则采用明确声明的合成 fixture | Lua、JSON、C#、城镇需求均保留；移除目录中的合法性证明后不能把无效 ID 当成真实货物。不得因此宣称废料真实 ID 为 0。 |
| AC-R07 | 数值/数字字符串 ID、小数、空值、非法字符串、目录键值形式差异 | 合法表示统一；非法值不被取整或误作另一个 cargo ID；资源目录映射有对应格式证据。 |
| AC-R08 | 不同 ID 的同名货物、模组新增货物 | 不串链；新增货物无需改中文名称白名单即可识别。 |
| AC-R09 | 经真实证据确认的返回格式、字段可读对象及受保护可调用对象 | 正确解析或明确降级；需要新增调用入口时补齐 proof；禁止只在普通函数 mock 下通过。 |
| AC-R10 | 混合合法与未知规则条目 | 已确认关系保留，未知项计入部分读取；不能静默忽略后标成完整。 |
| AC-R11 | 读取成功的空输入/输出、全部读取失败 | 合法空集合表示无对应规则；失败表示未知；页面不能把二者显示为同一种空态。 |
| AC-R12 | 当前有 0 个/多个下游，但其他产业输入未读全 | 两种情况下均提示结果可能不完整；有结果时继续可用，无结果时不下“没有下游”的确定结论。 |
| AC-R13 | 库存为零、已满、停产、产量为零、无线路，以及普通仓库可存该货物 | 前五项不取消真实关系；仓库兼容性不产生虚假生产/消费边。 |
| AC-R14 | 真实城镇需求、没有城镇用途、需求读取失败 | 各货物继续按单城镇规则判断；废料不被擅自加入城镇供给；空需求区回归仍通过。 |
| AC-R15 | 正负坐标、真实零坐标、未知坐标 | 排序和距离正确；未知坐标候选保留，定位能力独立处理。 |
| AC-R16 | 101/1001 个候选及高货物数量 | 所有 JSON 分片和页面结果可取完，集合相同，无重复、截断、漏项或响应超限。 |
| AC-R17 | 刷新、规则或等级改变、旧 revision 返回、切换地图/玩家 | 新索引准确更新，旧关系不混入；原有旧响应拒绝和地图隔离继续有效。 |
| AC-R18 | 循环关系、逐级分析和返回 | 直接上下游方向正确，循环不会递归失控；定位与返回不改变错误的分析基准。 |
| AC-R19 | 全货物审计 | 每个审计货物均有集合核对或未验证原因；没有未解释的漏识别、误识别被标成已通过。 |

AC-R06 是针对当前实现中两端 ID 过滤的防护用例；只有真实资源目录证据才能决定游戏中的 0 是否合法。AC-R09 中的结构和调用形式只要求支持被确认存在的形态，不以猜测变体扩充适配。

### 7.3 测试本身的可信度

- 真实废料 fixture 应在修复前代码上稳定失败，在修复后通过，并检查具体遗漏实体而不只是“数量大于 0”。若问题跨层，失败用例必须覆盖对应跨层路径。
- 保留至少一个反例：从独立 fixture 中移除某产业对该货物的真实消费规则后，它不再出现在下游；只增加库存兼容条目则不能产生消费关系。
- 校验方向：消费废料的产业不能因为它的输出被误读而成为废料供应者。
- 一条原始记录无法解释时，应有状态断言；不能只检查请求成功或 JSON 能解析。
- 现有 Lua 检查、C# 逻辑和布局回归继续运行；窗口/DPI 组合数量不等于独立产业链用例数量。
- fixture 和预期集合随仓库提交，测试可重复执行；报告同时给出执行命令、环境与提交。

## 8. 代码衔接与实施顺序

| 位置 | 本轮职责 |
| --- | --- |
| `src/功能接口v6.lua` | 资源身份、原始规则适配、全量关系采集、读取状态、诊断及分页；不以库存兼容替代消费。 |
| `src/IndustryRelations.cs` | 规范化 ID 读取、各方向完整性、关系集合去重及角色证据；保证跨层不二次过滤合法货物。 |
| `src/IndustryPage.cs` | 已确认候选、未完成状态及正确空态；保留现有分类、距离、定位、历史和大列表行为。 |
| `scripts/industry-lua-check.lua` 与新增 fixtures/跨层检查 | 复现真实缺陷并覆盖通用边界；复用生产调用链，不另写一套被测解析器。 |
| `src/RuntimeCallables.h` | 仅当引入新的受保护调用入口时，补充相应验证路径。 |

实施顺序：

1. 取得真实废料样本，逐层确定丢失点，提交能在旧代码失败的测试。
2. 修复通用货物身份或规则解析路径，同时完善部分读取状态，贯通 Lua → JSON → C# → 页面。
3. 对全货物/全产业生成审计差异，修复与本缺陷同类的遗漏，增加独立 fixture；其他尚不能确认的情况明确列出。
4. 完成自动化回归、原存档实测和页面全流程验证，提交审计结果及验证边界。

## 9. 完成定义

本轮完成须同时满足：

- 原废料漏识别有真实复现、具体根因、修复前后对比和能捕获旧缺陷的自动化测试。
- 废料在目标地图的已确认下游集合与独立预期一致，所有结果可以浏览、定位并继续分析。
- 全货物审计已执行，范围、遗漏、误识别及未验证项明确；不能仅检查废料后声称其他链路完整。
- 核心验收用例有结果或明确不适用的证据，原有分页、作用域、需求空表、滚动恢复等回归通过。
- 数据未知不会伪装成确定空结果；所有测试结果明确区分模拟、离线界面与游戏实测。

如果真实游戏证据尚未取得，交付状态只能是“离线实现/回归完成，游戏验收待验证”，不能把本规格整体标为通过。

实现 PR 的正文和每轮审查意见需同步到对应 GitHub PR，包含根因、修改范围、执行过的验证、审计摘要及剩余待验证项。
